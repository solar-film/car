### การเทียบ source ในเครื่อง

เทียบไฟล์ที่ tracked เดิม 86 ไฟล์กับ workspace: ตรง byte 21 ไฟล์; หลัง normalize เฉพาะ CRLF → LF ตรงเนื้อหา 82 ไฟล์ ต่างเนื้อหา 4 ไฟล์ ได้แก่ `Code.gs`, `LeadSheet.gs`, `CarContactHistory.gs`, `CarBookingStatusSync.gs` จึงไม่ควรสรุปว่า byte ที่ต่างทั้งหมดเป็นโค้ดต่าง

workspace มี `CarCrmAuth.gs`, `CarLeadService.gs` และ Node service/reader ซึ่งไม่ได้อยู่ใน development checkout นี้ ผลทดสอบ workspace กับ repository จึงเป็นหลักฐานคนละชุด ไม่ใช่หลักฐานว่า source live ตรงกับชุดใด ชุดนี้ไม่อัปโหลด server source หรือข้อมูลภายในจาก workspace เพิ่มเข้า public repo

- ไม่แก้ตัวเลขรายงาน นโยบาย qualification/lost reason, attribution, โฆษณา หรือ GOOD ERP

## เกณฑ์ตรวจรับและงานที่ยังต้องอนุมัติ

รับตรวจชุด offline นี้ได้จากคำสั่งใน README และรายงานข้อบกพร่องพร้อม fixture; **ยังไม่รับรอง P0 ระบบจริง** จนกว่าจะ:

1. อนุมัติอ่าน source/manifest/version ของ Apps Script live และ metadata schema/gid พร้อมหลักฐาน response/log แบบปิดบังข้อมูล เพื่อยืนยันสาเหตุของ read error และ deployment drift
2. เจ้าของยืนยันปลายทาง staging ที่แยกจาก production พร้อมบัญชีผู้ดูแล และนำ source ที่ตรวจแล้วมาจัดชุด ไม่ใช้ source repository เป็น live bundle โดยอัตโนมัติ
3. ตรวจ snapshot ที่ได้รับอนุญาตครบทั้ง Lead/Customer/Bookings/PayIn/history พร้อมขอบเขตวันและหลักฐาน source; ไม่ใช้ยอดเฉพาะหน้าจอที่กรองแล้ว
4. ทดสอบ workflow/browsers/restore ใน staging ผ่าน ตาม [STAGING_PLAN.md](STAGING_PLAN.md) แล้วแก้ข้อบกพร่องใน integration PR ที่เจาะจง
5. ขออนุมัติ merge/deploy เป็นขั้นตอนแยก; การแก้ schema/backfill/cleanup หรือทดสอบเขียน Production ต้องมีอนุมัติเฉพาะรายการและ backup ก่อน ไม่ขอ credential ผ่านแชต
